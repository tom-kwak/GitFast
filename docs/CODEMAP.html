gf 코드 지도

화면의 어느 부분이 어느 파일에 있는지 보여줍니다. 아래 창 그림에서 영역을 누르면 담당 코드와 요청 예시가 나옵니다. 요청할 때 굵은 이름을 그대로 쓰면 바로 찾아갑니다.

1 · 화면 → 코드 영역을 눌러 보세요

2 · 층 구조 위에서 아래로만 부릅니다

화면 코드는 git을 직접 실행하지 않습니다. 버튼을 누르면 gf-app이 gf-git의 Repository 메서드를 부르고, 그 안에서 git CLI(또는 읽기 일부는 gix)를 실행합니다.

gf-app화면과 상호작용
features/*app/*repo_tab.rsundo.rsnav.rswidgets/*theme/*highlight/*
↓ Repository::x().await
gf-gitgit 실행과 결과 해석
routes.rsbackend/mod.rs (trait)ops/*.rscli/runner.rscli/parse/*gix_*.rsgraph.rspatch.rsconflict.rs
↓ 공통 타입
gf-core모델 · 오류 · 이벤트
model/ (Commit, Branch, StatusEntry, FileDiff…)error.rsevent.rs (EventBus)
옆에서 돕는 크레이트 
gf-config — 설정·경로 (settings.toml)gf-watch — 파일 감시 → 새로고침gf-test-support — 테스트용 임시 저장소gf-commands · gf-flow · gf-hosting* · gf-auth — 비어 있음

3 · 버튼 하나가 지나가는 길 예: 변경 목록에서 파일 discard

변경 목록이 클릭을 받아 자기 상태를 바꾸고, 밖에서 할 일은 Output으로 App에 넘깁니다.
features/changes/mod.rs
Message → Output::Discard
App이 메시지를 해당 피처로 보내고, 돌아온 Output을 처리 함수로 넘깁니다.
app/mod.rs update()
→ app/outputs.rs on_changes
지우거나 바꾸는 작업이면 공통 확인창을 띄웁니다. 확인하면 Purpose에 맞는 작업을 실행합니다.
app/dialogs.rs
Confirm::delete / ::change, Purpose
작업을 비동기로 실행합니다. 이때 되돌리기용으로 전후 상태를 기록합니다.
app/ops.rs op_recorded
(merge·rebase는 advanced.rs)
어떤 git 구현을 쓸지 고르고, git 명령을 실행합니다.
gf-git routes.rs → ops/index.rs
→ cli/runner.rs
완료 메시지로 알림(flash)과 명령 로그를 남기고, 되돌리기 기록에 넣고, 저장소를 다시 읽습니다.
Message::OpDone → on_op_done
→ undoing.rs record_step → request_refresh
새 Snapshot으로 모든 패널이 다시 그려집니다. 바깥에서 파일이 바뀌면 감시기가 바뀐 곳에 맞는 부분만 다시 읽게 합니다(아래 4).
ops.rs on_loaded
repo_tab.rs Snapshot

4 · 새로고침은 필요한 부분만 무엇이 바뀌면 무엇을 다시 읽나

저장소 데이터(Snapshot)는 다섯 부분(Parts)으로 나뉩니다. 바뀐 곳에 맞는 부분만 git에서 다시 읽고, 나머지는 이전 Snapshot의 것을 그대로 씁니다. 히스토리는 HEAD·브랜치·태그·stash가 같으면(history_key) 다시 만들지 않습니다.

무엇이 바뀌었나다시 읽는 부분어디서 정하나
작업 트리 파일 저장status (gitignore된 경로는 무시: target/ 빌드는 새로고침 없음)mod.rs → ops.rs worktree_parts, gf-watch drop_ignored
.git/index (stage 등)statusapp/mod.rs 감시 이벤트 처리 (Parts::STATUS)
refs (커밋·브랜치·태그)status · refs · modules (+ 키가 바뀌면 history)app/mod.rs, repo_tab.rs history_key
.git/configstatus · configapp/mod.rs
모든 브랜치 토글, 더 불러오기history만outputs.rs → request_parts(id, Parts::HISTORY)
⌘R, 새 탭전부 (RELOAD)ops.rs refresh_active
gf가 실행한 작업이 끝남전부 (ALL)ops.rs request_refresh

읽는 중에 또 요청이 오면 겹쳐 실행하지 않고 RepoTab.queued에 모아 두었다가 끝난 뒤 한 번 더 읽습니다. 언제 읽을지는 매 메시지 뒤에 App::load_due가 정합니다. 보이는 탭이 먼저 읽고, 백그라운드 탭은 파일 변경을 탭이 보일 때까지 미룹니다(refs·config 변경은 바로 읽음). 열린 작업 트리 diff는 그 파일이 바뀌었을 때만(Touched) 다시 읽습니다. 읽은 부분과 걸린 시간은 로그(RUST_LOG=gf=debug)의 snapshot loaded 줄에 남습니다.

화면을 그릴 때마다 긴 목록 전체를 훑는 계산(가장 긴 줄 너비, diff 행 목록)은 widgets/memo.rs의 Memo에 담아 데이터가 바뀔 때만 다시 합니다. 결과가 틀리면 안 되는 값은 Same(Arc 동일성) 키, 너비처럼 모양만 영향받는 값은 Id(주소·길이) 키를 씁니다.

5 · 화면 밖에서 공통으로 쓰는 코드

파일무엇을 하나이럴 때 언급하세요줄

6 · 요청 이렇게 쓰면 빠릅니다

어디: 로컬 diff의 hunk 헤더 버튼 무엇: discard 버튼을 stage 버튼 왼쪽으로, 빨간색은 유지 왜: 실수로 discard를 누름

위치만 정확하면 파일 이름은 몰라도 됩니다. 이 페이지의 영역 이름(변경 목록, 커밋 박스, 상태줄 …)이나 화면에 보이는 글자를 그대로 적어 주세요. 키 동작은 "키 처리", 색은 "테마", 확인창 문구는 "확인창"이라고 하면 됩니다.
